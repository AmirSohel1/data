Relationship map

Aircraft → FlightOne aircraft may be assigned to multiple flight schedules.
Booking → PassengerOne booking contains one or more passenger records; local FK on Passenger.
User → BookingLinked by userId across service boundary; not a database FK.
Flight ↔ FareFare references flightId; the documented fare schema marks it unique.
Booking → CheckInCheck-in keeps a bookingId reference in its own database.
Booking → PaymentPayment stores bookingId and optional PNR for reconciliation.

Reservation collaboration

Booking Service→Flight Service →Fare Service→Payment

Synchronous REST / OpenFeign is used where the booking flow needs immediate validation or pricing responses.

Booking created→ RabbitMQ →Flight / notification consumers

Asynchronous events decouple follow-up work from the passenger-facing request.

Database-per-service rule: dashed logical relationships across service boundaries are API/event references, not relational foreign keys. AuthAccount is a conceptual summary of authentication responsibilities because the documentation describes the service behavior rather than a full auth entity schema.
