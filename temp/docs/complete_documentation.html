01. Project Overview & Business Domain

1. Executive Summary

AeroBook is an enterprise-grade, cloud-native airline flight reservation, passenger services, airport operations, and fleet management platform. Designed around modern distributed microservices principles, AeroBook provides a seamless, real-time end-to-end journey for airline passengers, airport ground staff, and flight operations administrators.

The application spans 11 Java Spring Boot backend microservices, 1 Angular 18 Single Page Application (SPA), and 8 decoupled MySQL database schemas, tied together through a reactive Spring Cloud API Gateway with client-side load balancing via Netflix Eureka Service Discovery.

2. Business Problem & Objectives

Modern commercial aviation demands robust, highly resilient software architectures capable of handling concurrent flight searches, dynamic fare pricing, high-volume transactional booking reservations, secure cryptographic payment processing, and instantaneous airport ground operations.

Key Business Challenges Addressed:

  1. Fault Isolation: Failure in ancillary services (such as notification dispatch or incident reporting) must never prevent a passenger from booking a flight or boarding an aircraft.
  2. Scalability & Decoupling: High-traffic passenger searches during holiday travel surges require independent horizontal scaling without overloading reservation or payment databases.
  3. Data Integrity & Consistency: Booking flight seats, processing payments, and issuing passenger name records (PNRs) must maintain strict consistency across distributed services.
  4. Multi-Persona Airport Experience: Distinct personas (Passengers, Ground Operations Staff, Airline Administrators) require specialized interfaces, strict role-based access control (RBAC), and tailored workflows.
  5. Regulatory Compliance & Standards: Generating authentic IATA Bar Coded Boarding Passes (BCBP), formal GST/tax invoices, and meeting WCAG AA accessibility standards for digital passenger channels.

5. Functional & Non-Functional Requirements

Functional Requirements

  • FR-01 (Authentication): Secure registration with BCrypt password hashing, JWT access token generation (24-hour expiration), and refresh token rotation.
  • FR-02 (Role Routing): Post-login role inspection automatically routing passengers to /customer, ground crew to /staff, and administrators to /admin.
  • FR-03 (Inventory Synchronization): Booking reservations must decrement available seats in real time and reject overbooking.
  • FR-04 (Cryptographic Verification): Razorpay payment signatures must be calculated using HMAC-SHA256 and verified prior to marking transactions CAPTURED.
  • FR-05 (Automated Document Generation): E-Tickets and Boarding Passes must be dynamically generated as vector PDFs using OpenPDF with embedded barcodes.
  • FR-06 (Asynchronous Messaging): Confirmed bookings must emit BOOKING_CREATED events to RabbitMQ for flight and notification consumers.

Non-Functional Requirements

  • NFR-01 (Resilience & Decoupling): Microservices must maintain isolated data stores (Database-per-Service) and graceful fallback when ancillary services are offline.
  • NFR-02 (Performance & Latency): Sub-second response times for flight searches via non-blocking reactive API Gateway routing.
  • NFR-03 (Accessibility - WCAG AA): Frontend contrast ratios must exceed 4.5:1 for normal text and 3:1 for graphical elements across both light and dark themes.
  • NFR-04 (Code Quality & Security): Zero high-severity vulnerabilities, JaCoCo XML backend test coverage reporting, and SonarQube quality gate integration.
  • NFR-05 (Zero Theme Flicker): Immediate pre-paint execution of theme preferences in browser DOM to avoid theme flashing.

6. Implementation Status & Limitations

Current Implementation Status

  • Backend Microservices (11/11): Fully functional, compiling, tested, and integrated with JaCoCo and SonarQube Maven plugins.
  • Frontend SPA (1/1): Fully functional Angular 18 standalone component architecture with 0 mock dependencies, WCAG AA compliance, and automated Karma/ChromeHeadless tests.
  • Database Layer (8/8): Schema creation scripts and full master seed data (scripts/seed.sql) covering 20 users, 16 aircraft, 25 flights, 25 fares, 16 coupons, 22 bookings, 18 check-ins, 22 payments, and 22 notifications.
  • Quality Analysis: Complete SonarQube configuration and master automation scripts (run-sonar-analysis.ps1, run-sonar-analysis.bat).

Known Operational Limitations

  1. Localhost Routing: Microservices currently default to localhost ports; Kubernetes manifest definitions and cloud container registries are planned for future deployment phases.
  2. RabbitMQ Optional Mode: RabbitMQ messaging defaults to disabled in development environments lacking a local broker, falling back to direct synchronous REST calls.
  3. Razorpay Live Gateway: Razorpay operates in test/mock mode using cryptographic simulation tokens unless configured with live merchant API keys in .env.

Key Architectural Patterns Implemented:

  1. API Gateway Pattern: Single unified ingress point (http://localhost:8083) shielding internal microservice network topology, terminating CORS, validating JWTs, and tracing requests.
  2. Service Discovery Pattern: Centralized Netflix Eureka registry (http://localhost:8761). Services register dynamically upon boot; the Gateway uses lb://SERVICE-NAME for reactive client-side load balancing.
  3. Database-per-Service Pattern: Each business microservice owns a dedicated, physically isolated MySQL database schema (aerobook_auth_db, aerobook_user_db, etc.). Direct cross-service database querying is strictly prohibited.
  4. Stateless JWT Security & Token Propagation: Cryptographically signed HMAC-SHA256 tokens authenticated at the Gateway. User identity is mutated into downstream HTTP headers (X-User-Id, X-User-Email, X-User-Role), liberating backend microservices from duplicate database token lookups.
  5. Hybrid Synchronous & Asynchronous Communication:
    • Synchronous (OpenFeign / REST): Used where immediate responses are strictly required (e.g. validating seat availability before confirming a reservation).
    • Asynchronous (RabbitMQ Event Bus): Used for decoupled background tasks (e.g. BOOKING_CREATED events triggering inventory bookkeeping without blocking passenger responses).

Gateway Cross-Cutting Filters:

  1. CorrelationIdGlobalFilter: Generates or propagates an X-Correlation-Id across all hops to ensure distributed trace visibility in logs.
  2. CorsDedupeGlobalFilter: Eliminates duplicate Access-Control-Allow-Origin headers that can occur when both the Gateway and embedded Tomcat instances attach CORS headers.
  3. AuthenticationFilter: Verifies cryptographic HMAC-SHA256 signatures of JWT tokens, enforces token expiration limits, and injects user identity into downstream headers.

4.1 Synchronous Invocations (OpenFeign)

  • Auth Service -> User Service: During /api/auth/register, UserClient invokes POST /api/v1/users to synchronize customer demographics into aerobook_user_db.
  • Auth Service -> Notification Service: Invokes POST /api/notifications/email/verify to dispatch 6-digit OTP codes via SMTP.
  • Booking Service -> Flight Service: FlightServiceClient invokes GET /api/flights/{id} to verify schedule status and check that available_seats > 0.
  • Booking Service -> Fare Service: FareServiceClient invokes GET /api/fares/flight/{flightId} to calculate exact cabin pricing and apply validated coupons.
  • Fare Service -> Flight Service: FlightServiceClient verifies flight schedule existence before permitting administrators to create or update tiered pricing models.

4.2 Asynchronous Event Flow (RabbitMQ)

  • Producer: BookingEventPublisher in booking-service publishes message payload BOOKING_CREATED:<pnr> to direct exchange booking-exchange with routing key booking-created.
  • Consumer: BookingEventConsumer in flight-service listens on queue booking-created to asynchronously update internal flight metrics and booking counters.
  • Resilience: Configured with fallback mechanisms so that if RabbitMQ is unavailable in development, booking operations complete without throwing exceptions.

The Auth Service is the central identity provider and security authority for the AeroBook platform. 5. Coupon Validation Logic

When a passenger enters a coupon code during checkout, POST /api/fares/coupons/validate executes the following validation pipeline:

  1. Lookup coupon by uppercase code.
  2. Verify status is ACTIVE.
  3. Verify current date is within [validFrom, validUntil].
  4. Verify usageCount < usageLimit.
  5. Verify order subtotal >= minFare.
  6. Compute discount: min(subtotal * (discountPercentage / 100), maxDiscount).
  7. Return calculated discount and new payable total.

sequenceDiagram

    actor Customer as Passenger (Frontend)

    Customer->>Gateway: POST /api/payments/orders (bookingId, amount)

    Payment->>DB: INSERT payments (status: CREATED, orderId)

    Payment->>Payment: Compute HMAC_SHA256(order_id + "|" + payment_id, secret)

1. Architectural Philosophy: Database-Per-Service

AeroBook strictly adheres to the Database-per-Service architectural pattern. Each business domain microservice owns its private, isolated MySQL database schema. No microservice is permitted to execute direct SQL queries, joins, or mutations against a database owned by another microservice.

All cross-domain queries and data synchronizations are orchestrated via:

  1. Synchronous OpenFeign REST calls for operational dependencies (e.g., Booking Service querying Flight Service for seat availability).
  2. Asynchronous RabbitMQ AMQP messaging for state propagation (e.g., Booking Created events reducing flight seat inventory).
  3. Identity Token Claims for user context propagation (X-User-Id, X-User-Role).

Platform Security & Authentication Architecture

1. Security Philosophy & Edge Enforcement

AeroBook implements a defense-in-depth, perimeter-enforced security architecture. The platform uses stateless JSON Web Tokens (JWT) for identity verification and access delegation.

Authentication is centralized at the API Gateway (api-gateway:8083):

  1. Edge JWT Verification: Inbound requests with Authorization: Bearer <token> are cryptographically validated by the Gateway's reactive JwtAuthenticationFilter.
  2. Context Enrichment & Mutation: Valid tokens have their claims extracted (userId, email, role). The Gateway mutates the downstream HTTP request, appending standard HTTP headers:
    • X-User-Id: Numeric ID of the authenticated user.
    • X-User-Email: Email address of the authenticated user.
    • X-User-Role: Assigned role (ROLE_USER, ROLE_STAFF, ROLE_ADMIN).
  3. Downstream Service Defense: Microservices trust the gateway-propagated X-User-* headers, eliminating repeated asymmetric cryptography calculations while enforcing RBAC at the service layer.

  • Secret Key: Defined via jwt.secret (minimum 256 bits, Base64/Hex encoded).
  • Token Lifespans:
    • Access Token TTL: 24 hours (86,400,000 ms).
    • Refresh Token TTL: 7 days (604,800,000 ms).
  • Token Claims Payload:

Passwords are never stored in plaintext. They are salted and hashed using BCryptPasswordEncoder with a cost factor (strength) of 10:

  • Prevents rainbow table attacks, dictionary attacks, and timing leaks.

Operational Troubleshooting & Diagnostics Runbook

This guide details common operational failure modes encountered across the AeroBook microservices ecosystem, root cause analyses, and step-by-step remediation procedures.

1. Port Binding Conflicts & Stale Processes

Symptom

A microservice fails during startup with Web server failed to start. Port 808X was already in use.

Root Cause

A previously running instance or crashed JVM retained the TCP socket binding.

Remediation

Windows (PowerShell):

# Identify process ID holding the port (e.g. 8083)
Get-NetTCPConnection -LocalPort 8083 -ErrorAction SilentlyContinue | Select-Object OwningProcess

# Terminate the process
Stop-Process -Id <PID> -Force

Linux / macOS:

lsof -i :8083
kill -9 <PID>

2. Eureka Service Registration Latency & HTTP 503 Errors

Symptom

Immediately after launching services, frontend requests through http://localhost:8083/api/... return HTTP 503 Service Unavailable or Unable to find instance for <SERVICE-NAME>.

Root Cause

Netflix Eureka uses a 30-second heartbeat cycle. When a microservice boots up, it takes between 15 to 30 seconds for the Eureka server to register the lease, and another 15 to 30 seconds for the API Gateway's reactive discovery locator cache to synchronize.

Remediation

  1. Wait 30 seconds after launching all microservices.
  2. Verify the service appears as UP in the Eureka Web Console at http://localhost:8761.
  3. Check the Gateway health registry at http://localhost:8083/api/gateway/services.
  4. Run the health probe:
    .\scripts\smoke-check.ps1

3. Database Connectivity & Authentication Failures

Symptom

Microservice logs display: java.sql.SQLNonTransientConnectionException: Could not create connection to database server or Access denied for user 'root'@'localhost'.

Root Cause

  1. Local MySQL Server service is stopped.
  2. The password in application.properties does not match your local MySQL root password.
  3. The required database schema has not been initialized.

Remediation

  1. Check MySQL service status:
    Get-Service -Name MySQL*
Start-Service -Name MySQL80  # or your installed service name
  2. Verify database schemas exist by re-running the seed script:
    .\scripts\seed.ps1
  3. Override credentials via environment variables without editing code:
    $env:MYSQL_PASSWORD="YourActualPassword"

4. RabbitMQ Broker Connection Failures

Symptom

booking-service or flight-service fails with: org.springframework.amqp.AmqpConnectException: java.net.ConnectException: Connection refused: no further information.

Root Cause

RabbitMQ server is not running or the AMQP default port 5672 is blocked.

Remediation

  1. Verify RabbitMQ Windows Service is running:
    Get-Service -Name RabbitMQ
Start-Service -Name RabbitMQ
  2. Check RabbitMQ management console at http://localhost:15672 (default credentials: guest / guest).

5. Frontend CORS Errors

Symptom

Browser console logs Access to fetch at 'http://localhost:808X/...' has been blocked by CORS policy.

Root Cause

The frontend attempted to connect directly to an individual microservice port (e.g. 8087 or 8088) rather than routing through the centralized API Gateway on port 8083.

Remediation

  1. Verify all API requests in the Angular client target http://localhost:8083.
  2. Ensure the API Gateway globalcors configuration is loaded.

6. JWT Authentication & Token Expiration

Symptom

Protected endpoints return HTTP 401 Unauthorized with message JWT expired or SignatureException.

Root Cause

Access tokens expire after 24 hours. Alternatively, if jwt.secret differs between auth-service and api-gateway, signature verification fails.

Remediation

  1. Ensure jwt.secret matches in both auth-service/src/main/resources/application.properties and api-gateway/src/main/resources/application.properties.
  2. Log out and log back in, or trigger the refresh token endpoint:
    POST http://localhost:8083/api/auth/refresh-token
Content-Type: application/json

{ "refreshToken": "..." }

7. Role Synchronization & Admin Dashboard Redirection

Symptom

After logging in with an Admin account (admin@aerobook.com), the user is not automatically redirected to /admin or receives access denied.

Root Cause

Role claims in the JWT token or database may contain ROLE_ADMIN while frontend guard checks expected ADMIN (or vice versa), or local storage was not cleared from a previous unprivileged session.

Remediation

  1. AuthService in the frontend normalizes roles by stripping the ROLE_ prefix or checking both (ROLE_ADMIN and ADMIN).
  2. Clear browser localStorage (localStorage.clear()) and re-login.
  3. Verify that the database aerobook_auth_db.credentials table has role = 'ROLE_ADMIN'.

8. Razorpay Signature Verification Discrepancies

Symptom

Payment verification returns HTTP 400 Bad Request with Invalid Payment Signature.

Root Cause

The razorpay.key.secret configured in payment-service does not match the secret of the Razorpay Key ID used by the frontend checkout script.

Remediation

  1. Verify that RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET in payment-service/src/main/resources/application.properties belong to the same active Razorpay test account pair.

Architecture Decision Records (ADR)

This document captures the key architectural decisions, rationale, trade-offs, and alternatives considered during the design and evolution of the AeroBook platform.

ADR 01: Microservices Architecture over Monolithic Architecture

  • Status: Accepted
  • Context: An airline booking and operations platform encompasses multiple distinct business boundaries with divergent scaling, security, and operational requirements (e.g., high-volume read-heavy flight searches vs. high-concurrency transactional booking reservations and low-latency gate boarding verifications).
  • Decision: Decompose the application into 11 independently deployable microservices organized around domain boundaries: Service Discovery, Config Server, API Gateway, Auth, User, Flight, Fare, Booking, Check-In, Notification, and Payment.
  • Consequences:
    • Positive: Independent scaling, domain isolation, localized failure domains, autonomous service deployments.
    • Trade-offs: Increased operational complexity, distributed transactions requiring eventual consistency, inter-service network latency.

ADR 02: Database-per-Service Pattern over Shared Database Schema

  • Status: Accepted
  • Context: In monolithic enterprise databases, multiple subsystems execute cross-table joins, tightly coupling database schemas and preventing individual teams or services from modifying data models without risk of system-wide breakage.
  • Decision: Mandate strict Database-per-Service isolation across 8 private MySQL schemas (aerobook_auth_db, aerobook_user_db, aerobook_flight_db, aerobook_fare_db, aerobook_booking_db, aerobook_checkin_db, aerobook_notification_db, aerobook_payment_db). Microservices are prohibited from querying external databases directly.
  • Consequences:
    • Positive: Complete schema autonomy, independent database performance tuning, zero cross-domain table locking.
    • Trade-offs: Elimination of relational foreign key constraints across services; cross-service queries must be orchestrated via APIs or messaging.

ADR 03: Reactive Non-Blocking API Gateway (Netty & Spring Cloud Gateway)

  • Status: Accepted
  • Context: The API Gateway serves as the single perimeter ingress for all platform traffic. A thread-per-request blocking gateway model (e.g., Spring MVC / Zuul 1) can suffer thread pool exhaustion under heavy concurrent request spikes.
  • Decision: Adopt Spring Cloud Gateway built on Spring WebFlux, Project Reactor, and Netty.
  • Consequences:
    • Positive: Asynchronous non-blocking I/O capable of handling tens of thousands of concurrent client connections with minimal memory and CPU overhead.
    • Trade-offs: Reactive programming paradigms require careful filter chain structuring and non-blocking filter implementations.

ADR 04: Hybrid Synchronous (OpenFeign) & Asynchronous (RabbitMQ) Messaging

  • Status: Accepted
  • Context: Certain business actions require immediate consistent answers (e.g., Booking Service must verify flight existence and seat counts before accepting payment), while other operations can be processed asynchronously without blocking the user (e.g., flight seat count deduction, e-ticket PDF generation, email dispatch).
  • Decision: Use Spring Cloud OpenFeign with Eureka client-side load balancing for synchronous query-response flows, and RabbitMQ with durable AMQP queues for asynchronous state propagation and background notifications.
  • Consequences:
    • Positive: Optimal user response times, fault isolation (booking succeeds even if notifications are delayed), guaranteed message delivery via durable queues.
    • Trade-offs: Requires maintaining both an HTTP service discovery mesh and an AMQP broker cluster.

ADR 05: Perimeter JWT Authentication & Downstream Header Mutation

  • Status: Accepted
  • Context: Re-evaluating cryptographic JWT signatures and hitting database caches on every internal microservice hop introduces significant CPU overhead and latency.
  • Decision: Centralize JWT signature verification and role parsing exclusively at the API Gateway. The Gateway extracts claims and injects trusted HTTP headers (X-User-Id, X-User-Role, X-User-Email) into downstream requests.
  • Consequences:
    • Positive: High internal throughput, downstream services remain lightweight and decoupled from token parsing logic.
    • Trade-offs: Internal service ports must be secured from direct external ingress via network firewalls or container virtual networks.

ADR 06: Angular 18 Standalone Components & Signals over NgModules

  • Status: Accepted
  • Context: Traditional Angular applications suffer from NgModule boilerplate, verbose RxJS boilerplate for simple reactive state, and performance overhead from Zone.js dirty checking.
  • Decision: Build the frontend Single Page Application using Angular 18 with 100% Standalone Components and native Angular Signals (signal(), computed()) for component state management.
  • Consequences:
    • Positive: Tree-shakable bundle sizes, clear component dependency graphs, instantaneous fine-grained DOM updates without zone-wide re-renders.
    • Trade-offs: Developers must adhere strictly to Signal-based data patterns rather than legacy two-way bindings.

Architecture Evolution & Engineering Recommendations

This document outlines prioritized, actionable engineering recommendations to advance the AeroBook microservices platform from a high-functioning development state to an enterprise-grade, high-availability production ecosystem.

1. High Priority (Near-Term Production Readiness)

1.1 Database Schema Migrations (Flyway / Liquibase)

  • Current State: Microservices rely on Hibernate DDL auto-generation (spring.jpa.hibernate.ddl-auto=update).
  • Risk: Automatic schema generation can cause accidental column mutations, cannot roll back failed schema alterations, and is unsafe for zero-downtime database upgrades.
  • Recommendation: Integrate Flyway across all 8 persistent services. Set spring.jpa.hibernate.ddl-auto=validate and manage schema changes via versioned SQL scripts (V1__initial_schema.sql, V2__add_index.sql).

1.2 Circuit Breakers & Resilience4j

  • Current State: OpenFeign clients (FlightServiceClient, FareServiceClient) invoke downstream HTTP services directly.
  • Risk: Cascading service failure if a downstream microservice slows down or becomes unavailable during high load.
  • Recommendation: Equip all OpenFeign client interfaces with Resilience4j Circuit Breakers, TimeLimiters, and fallbacks to gracefully handle downstream service timeouts and return cached flight schedules or friendly error states.

1.3 Distributed Caching with Redis

  • Current State: Flight search queries (GET /api/flights/search) execute SQL table queries on aerobook_flight_db on every user keystroke and search submission.
  • Risk: High database CPU utilization during flight search peak hours.
  • Recommendation: Introduce a Redis cache cluster for flight route schedules, seat availability read models, and active coupon codes with a 60-second time-to-live (TTL), invalidated via AMQP events upon flight modification.

1.4 API Gateway Rate Limiting & Throttling

  • Current State: Gateway routes requests without request rate limitations.
  • Risk: Vulnerable to brute-force credential stuffing attacks on /api/auth/login and denial-of-service on search endpoints.
  • Recommendation: Enable Spring Cloud Gateway's built-in Redis RateLimiter using the Token Bucket algorithm, enforcing limits such as 10 requests/sec for anonymous search and 5 requests/min for login attempts.

2. Medium Priority (Operational Maturity)

2.1 Distributed Tracing with OpenTelemetry & Tempo

  • Current State: Request tracking relies on MDC log patterns and manual correlation ID parsing.
  • Recommendation: Integrate Micrometer Tracing with OpenTelemetry exporters to stream distributed trace spans to Grafana Tempo or Jaeger, giving operations teams visual flame graphs of request latencies across all microservice hops.

2.2 Dead Letter Queues (DLQ) & Message Retry Policies

  • Current State: Unhandled consumer exceptions in RabbitMQ queues could result in message requeuing loops or message drops.
  • Recommendation: Configure a Dead Letter Exchange (dlx.aerobook) and Dead Letter Queues (booking-created.dlq) with exponential backoff retries (3 attempts) before routing unprocessable events to an alert queue.

2.3 Centralized Secret Management

  • Current State: Configuration properties allow environment variable injection, but defaults exist in application.properties.
  • Recommendation: Store production credentials, Razorpay secret keys, and JWT keys in HashiCorp Vault or AWS Secrets Manager, injected dynamically into container pods at runtime.

3. Long-Term Architectural Goals

3.1 CQRS (Command Query Responsibility Segregation)

  • Separate the high-volume Flight Search read models from the transactional Flight Booking write engine, replicating read data to Elasticsearch or MongoDB for sub-millisecond faceted search.

3.2 WebSocket / Server-Sent Events (SSE) for Real-Time Flight Updates

  • Replace polling on the passenger and staff dashboards with reactive Server-Sent Events from notification-service, instantly updating departure gate numbers and flight delays on passenger mobile screens.
